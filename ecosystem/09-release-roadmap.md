> **A release name cannot be sorted, and believing otherwise has already cost a deploy.** Two
> things break it. The sequence is not zero-padded, so `2026.08.21` sorts *before* `2026.08.6` as
> a string. And `org/releases/` holds **two incomparable lineages** — the dated one and the semver

How thirty-one independently versioned repositories become one thing a person can deploy, roll
back and name.

Today they cannot. `CLOUDSFORGE_TAG` is a single value shared by fourteen images built by seven
repositories ([00-current-state.md](00-current-state.md) §3.6). A commit sha cannot work as a
pin, because no two repositories share one. A repository you forget to tag has no image at that
version and the stack comes up with a hole in it. A release is seven hand-pushed git tags and a
hope.

The replacement is stated in [02-target-architecture.md](02-target-architecture.md) AD-03: a
**release manifest** at `stack/releases/<version>.yaml`, generated by CI, committed, and the
only thing a deployment reads. Everything in this document is downstream of that one file.

## 1. The release train

### 1.1 What a release is

A release is a manifest, not a tag. It names exactly one image version for each deployable in
the estate, plus the migration jobs that must run before them and the feature-flag defaults they
boot with. It is produced by CI, it is immutable once promoted, and it is the unit of both
deployment and rollback. Rolling back is checking out the previous manifest and applying it.

Each repository releases on its own cadence and its own semver. Nothing coordinates their
version numbers, and nothing should: coordinating thirty-one version numbers is the monorepo
convenience that AD-01 deliberately gave up. What is coordinated is the *set* — the manifest is
the artefact that says "these thirty-one versions were tested together and are known to work".

### 1.2 What a manifest contains

| Field | Content | Why it is in the file |
| --- | --- | --- |
| `version` | The release name — `v0.6.3`, `v1.0.0` | The only identifier an operator quotes |
| `generatedAt`, `generatedBy` | Timestamp and the CI run URL that produced it | Provenance; a hand-edited manifest is a defect |
| `services[]` | For each of the 22 services: repo, semver, image reference, **image digest** | The digest is the real pin; the tag is for humans |
| `frontends[]` | The 10 web repos, same shape | SPAs are deployables since P3 |
| `telemetry[]` | Collector, Prometheus, Tempo, Loki, Grafana, Alertmanager versions | These are operated systems, and a Grafana upgrade has broken a dashboard before it has broken nothing |
| `migrations[]` | Per service, the highest `schema_migrations` version this release expects | Lets `cfctl` refuse to deploy a manifest whose migrations have not run |
| `contracts{}` | The `@cloudsforge/contracts-*` versions each service was built against | Makes "who is still on `contracts-chain` 1.4" a query, not an audit |
| `flags{}` | Feature-flag defaults, with an owner and an `introducedIn` release | Flag age is measurable, so flag debt is enforceable (§6) |
| `gate` | The Beacon journey suite revision and the run ids that passed it | A release is not promotable without the evidence attached to it |

`cfctl release` generates it; `cfctl up --release v0.6.3` applies it; `cfctl doctor` validates
that what is running matches it. A manifest that omits a service in the catalogue fails
validation — the "repo you forgot" failure mode is a schema error rather than an outage.

### 1.3 Cadence, and who cuts

**Release candidates are cut weekly.** Every Monday, CI generates a candidate manifest from the
latest green `main` of every repository, deploys it to staging, and runs the full Beacon journey
suite. A candidate that passes three consecutive runs is promotable. A candidate that fails is
not fixed in the candidate; the offending repository fixes forward and the next candidate picks
it up. Trains depart on time; passengers who miss one take the next.

**Numbered milestone releases are cut on a gate, not on a calendar.** `v0.6.0` exists when the
Phase 5 migration exit gate passes, whenever that is. The weekly candidates in between are
`v0.6.0-rc.N`; the patch stream after it is `v0.6.1`, `v0.6.2`, and so on.

**Who cuts.** One release manager per release, named in the manifest. Their job is not to
decide whether the code is good — that is the gate's job — but to confirm the gate evidence
exists, that no journey is muted, that the Renovate lag figure from
[03-repository-responsibilities.md](03-repository-responsibilities.md) §5 is under 24 hours, and
to press promote. Promotion to production is a two-person action from `v0.7` onward, because
from `v0.7` the release moves real balances.

## 2. Versioning policy

Semver per repository, images tagged with the version, digests pinned in the manifest. The
interesting question is what each level *means*, and it differs by artefact type.

| Level | A service | A contract package | A frontend |
| --- | --- | --- | --- |
| **Major** | A removed or renamed route, a removed response field, a changed auth scope requirement, or a migration that is not expand/contract-safe. Requires a coordinated consumer plan and cannot ship in a patch train. | Forbidden after `1.0.0` except by the deprecation procedure in §7. `contract-compat.yml` fails the build on a removed field, a narrowed type or a rename (AD-02). | A changed public URL structure, a removed page, or a change requiring a matching API major. Deep links are a contract. |
| **Minor** | A new route, a new optional field, a new event topic, a new leased job, an expand-phase migration. Backwards-compatible for every existing caller. | A new field, a new type, a new constant, a widened union. Consumers may lag by up to two minors (AD-02); the compat check is what makes lagging safe. | A new page, a new panel, a new flag-gated feature. |
| **Patch** | A bug fix, a dependency bump, an internal refactor, a copy change, a performance change. No schema change, no contract change. | A documentation or typing fix that changes no shape. | Styling, copy, accessibility, bug fixes. |

Three rules that are not negotiable:

1. **`@cloudsforge/contracts-chain` is exact-pinned, never caret-pinned.** `RATE_SCALE`,
   `shardsForCoinAmount()` and the per-coin confirmation depths must agree byte-for-byte between
   `wallet`, `settlement`, `custody` and `indexer`, or money is credited at the wrong depth.
   A minor drift there is a money incident, so the two-minor lag allowance does not apply.
2. **A service's major version never bumps in the same release as its consumers' adoption.**
   Provider ships the new shape as a minor, consumers move, the old shape is removed in a later
   major. Big-bang contract changes are how a polyrepo becomes a distributed deadlock.
3. **`0.x` is banned for published packages.** Caret on `0.x` is patch-only, which is precisely
   why no consumer in the estate can resolve `@cloudsforge/shared` 0.5.0 today (§3.7). Every
   package starts at `1.0.0`.

## 3. Environments

| Environment | Purpose | Data | How it is fed | Promotion rule |
| --- | --- | --- | --- | --- |
| **local** | Development, and the loop `cfctl up` gives a new engineer | Seeded fixtures; testnet chains only; no real keys | Any manifest, or `latest` per repo | Nothing promotes out of local |
| **sandbox** | The public developer environment (P11) and the demo surface | Synthetic, resettable to a known snapshot on demand | The current production manifest, deployed separately | Never a source; always a mirror |
| **staging** | The release gate. Mirrors production topology exactly — same gateway, same three networks, same replica counts | Synthetic data by default; a **restored, redacted production dump** for migration rehearsals only, destroyed after each rehearsal | Every weekly candidate, automatically | A manifest must have passed the journey suite here, three consecutive runs, to be promotable |
| **production** | The estate | Real | Only a manifest promoted from staging | Nothing is deployed to production that has not been deployed to staging as the identical manifest, digest for digest |

Staging becomes permanent infrastructure at Phase 0 and is a hard requirement from then on;
[02-target-architecture.md](02-target-architecture.md) §7.2 explains why no single repository's
CI can substitute for it. Sandbox does not exist until P11 and is deliberately not a promotion
step — a third-party-facing environment fed from a pre-production manifest would let a developer
build against code that never ships.

## 4. Milestone releases

Seven named releases across fourteen phases. Complexity and week estimates are carried from
[06-ecosystem-workflow.md](06-ecosystem-workflow.md); there are no dates here because there is
nothing in the estate that makes a date honest.

### v0.4 — Baseline and triage · phases P0, P1 · M + M, four to six weeks

**Theme.** Know what the system does, then stop it losing money.

**User-visible change.** Users stop being double-billed for performance fees. Four convenience
items, three cosmetic kinds and two ForgeMint features that nothing delivers disappear from the
API as well as the UI. `private_world` purchases are refunded. Two players stop landing on one
homestead tile.

**Go/no-go.** 45 Beacon journeys green three consecutive runs · OpenAPI generated (not written)
for all nine services · two weeks of baseline telemetry captured and queryable · the data census
signed and committed · `forge-pay`'s 102 existing tests running in CI · all twelve P1 fixes with
a named regression test each · the two-replica concurrency test passing for settlement and
withdrawal · a catalogue-versus-handler test proving no purchasable SKU lacks a delivery path.

This release ships from the *current* repositories with the *current* `CLOUDSFORGE_TAG`
mechanism. It is the last release that does.

### v0.5 — Foundations · phase P2 · XL, six to ten weeks

**Theme.** Build the machinery the topology requires, before anything is split.

**User-visible change.** None, and that is the phase's largest risk (§6 of
[06-ecosystem-workflow.md](06-ecosystem-workflow.md) records it as such). Indirectly: failures
start being found by us rather than reported by users.

**Go/no-go — this is the polyrepo gate.** A contract publish reaches every consumer unattended
in under 24 hours, demonstrated twice · zero repositories with a bespoke CI file ·
`cfctl new service <name>` yields a service passing CI and visible in Beacon within an hour,
demonstrated · **a release manifest deploys the full stack to staging and the previous manifest
rolls it back** · every service reports `/readyz` truthfully, verified by killing Postgres and
observing 503 · one trace spans gateway → nimbus → pay → keyvault in Grafana · two replicas of
`forge-mint` run without incorrectness · 45 journeys green.

If the first, third and fourth criteria are not met, the correct action is to stop and revisit
AD-01 rather than to split repositories anyway. That is the whole point of putting the gate here.

### v0.6 — Decomposition · phases P3, P4, P5 · L + XL + XL, sixteen to twenty-four weeks

**Theme.** Move the code and the money, one piece at a time, with the journeys as the gate after
every extraction rather than after all of them.

**User-visible change.** Deposits show real transaction hashes and explorer links for the first
time. Bitcoin and Solana become withdrawable and sweepable. The explorer stops looking like a
different company. The faucet drips. Everything else is invisible when it works, which is the
point.

**Go/no-go.** Thirteen new repositories building, releasing and deployed from the manifest · no
API process serves a SPA · trial balance exactly zero, continuously, for two weeks · backfilled
opening balances reproduce the P0 census exactly · zero Pay-versus-ledger divergence for two
weeks before the read cutover · the balances projection rebuilds from the journal and matches ·
two `settlement` replicas cannot sign two transactions against one nonce · `PAY_SERVICE_TOKEN`
no longer exists anywhere · indexer at parity with balance-probing for 30 days · a simulated
reorg past the confirmation depth detected, alerted and recovered without a wrong credit · no
route in any service can return private key material · master secret rotated end to end on
staging · every legacy repository archived read-only · p95 within 20% of the P0 baseline.

This is the largest release in the plan and the one with the longest waiting-rather-than-building
component: the two-week zero-divergence gate and the 30-day indexer parity window are soak
periods, not work items, and compressing them is the single most tempting mistake available.

### v0.7 — Money · phase P7 · L, six to eight weeks

**Theme.** Make the money trustworthy before building the surface that displays it.

**Why this before Hub.** P6 and P7 are both gated on P4 and P5 and neither depends on the other,
so both start at the v0.6 gate and run in parallel. P7 is L and P6 is XL, so P7 lands first
naturally. The ordering is also correct on its merits: a portfolio chart drawn from an
unreconciled ledger is a lie with a gradient on it
([02-target-architecture.md](02-target-architecture.md) §6.3).

**User-visible change.** Withdrawals work on every supported chain. Deposits stop freezing.
Convert-to-EMBER returns, this time behind a real reserve check — closing the P1 item 12
suspension. Stuck transactions get a UI instead of a curl command.

**Go/no-go.** All five chain families complete for deposit, withdrawal and sweep on testnet ·
injected drift detected within one reconciliation cycle and freezing the correct asset only ·
a full period close runs and reconciles · manual adjustments require dual approval and a reason
code and emit audit events, not log lines.

### v0.8 — Forge Hub · phase P6 · XL, ten to fourteen weeks

**Theme.** The ecosystem becomes visible to the person using it.

**User-visible change.** The largest single jump in the programme. One dashboard showing
everything owned, done and available next, replacing an account page that renders two initials
and a hardcoded launcher grid. MFA. Session and device management. A wallet list with labels,
QR codes, fee review and real confirmation progress. External wallet connection with signed-
challenge verification. The key export ceremony. One activity feed across every product.

**Go/no-go.** A user completes register → MFA enrol → provision → receive → confirm → convert →
send → confirm on testnet without leaving Hub · an external EVM wallet is verified and set as a
withdrawal destination · a key export completes including the 24-hour cooling-off, and the
wallet reads `exported` everywhere · the activity feed shows events from at least six services ·
dashboard p95 under 800 ms healthy, and it renders with any one upstream down.

### v0.9 — Create and Market · phases P8, P9 · L + XL, sixteen to twenty-two weeks

**Theme.** Creation gets a product, and then a destination.

**User-visible change.** A creator goes from an idea to a branded, deployed, documented token
with a project page in one sitting, owning it from their own wallet — then lists it. Auctions,
offers, escrow, royalties, computed risk indicators read from the indexer rather than from the
order record.

**Go/no-go.** A creator completes all ten launch steps on testnet unaided · Solana is either
unsuspended or formally withdrawn with the code removed · every ForgeMint tier's advertised
features exist · a custodial and a non-custodial sale both settle end to end · concurrent
purchase of one listing yields exactly one order · moderation and dispute flows exercised.

P11 (developer platform, XL) runs as a parallel track through this window and lands in v1.0.

## 5. The first production release, precisely

**What v1.0 means, and why that definition and not another.** Not "feature complete" — the
backlog outlives every version number. Not "no known bugs" — nothing ships under that rule.
v1.0 means: **all eleven "one platform" tests in [01-product-vision.md](01-product-vision.md) §2
are true, and the platform can be operated as a business rather than as a project.**

That definition is falsifiable, and it maps exactly onto phases. Tests 1–5 and 8 flip in P6.
Test 10 flips in P7. Tests 6, 7 and 9 flip in P10. Test 11 flips in P11. P13 supplies the second
clause — backups proven by restore drills, SLOs with a month of data, a runbook per alert, an
incident rehearsed end to end including a public status update, and financial reports that
reconcile to the ledger for a full period.

### In v1.0

| Included | Because |
| --- | --- |
| Everything in v0.4 through v0.9 | Cumulative by construction |
| P10 — product integration | Tests 6, 7 and 9. Also where the private world that has been sold since before this programme began is finally provisioned |
| P11 — developer platform | Test 11 |
| P13 — operations and commercial readiness | The second clause of the definition |

### Deliberately out of v1.0

| Excluded | Why | Where it goes |
| --- | --- | --- |
| **P12 — community and governance** | It maps to none of the eleven tests. It is a large, desirable phase whose absence does not make the platform unfit to run | v1.1 |
| **Hearth mainnet** | Not launched, and nothing in this plan assumes a date ([02](02-target-architecture.md) §7.6). Everything EMBER-denominated is testnet at v1.0 and says so in the UI | When the chain launches |
| **HD derivation for pre-P5 addresses** | Flat-random keys cannot become HD keys. Two schemes coexist permanently and every response states which | Never; it is a stated permanent condition |
| **Multi-host or Kubernetes** | A conclusion, not a prerequisite. `custody` and Hearth nodes are single-replica permanently regardless | Post-1.0, when load requires it |
| **On-chain community treasuries** | Hearth has no multisig and no finality gadget; an on-chain treasury today is a single key with extra steps | When Hearth gains threshold signing |
| **Fiat anything** | Payments are crypto-native by design; there is no invoice path to configure | Not planned |

### Entry conditions for cutting v1.0

1. Every phase gate P0–P11 and P13 passed, with evidence attached to the manifest.
2. Zero muted Beacon journeys. A muted journey at a gate is a stop condition, not a note.
3. Trial balance exactly zero, continuously, for the preceding 30 days.
4. Reconciliation clean across every asset and chain for a full period close.
5. A restore drill completed within the stated RTO, from an off-host backup, inside 30 days.
6. No feature flag in the manifest older than two releases (§6).
7. p95 within 20% of the P0 baseline on every route that existed at P0.
8. A security review of the export ceremony, the break-glass runbook and the public API surface,
   signed and dated.

### v1.0 rollback plan

The manifest rolls back to the last v0.9.x in one action, and the release manager may do it
without escalation for the first 72 hours. What that recovers, and what it does not, is §8 —
by v1.0 the ledger read cutover, the reveal deletion and the migration conversion are all long
past their reversible windows, so a v1.0 rollback is a rollback of P10, P11 and P13 only. That
is precisely why those three phases carry per-feature flags and the earlier ones carry soak
periods.

## 6. Feature flags

**Naming.** `<phase>.<service>.<capability>` — `p05.wallet.indexer_crediting`,
`p06.custody.key_export`, `p07.ledger.reconciliation_freeze`, `p09.market.noncustodial_settle`.
The phase prefix is the point: it makes the flag's expiry date self-documenting, and it makes an
orphaned flag obvious in a listing.

**Where they live.** In the release manifest's `flags{}` block until P13, at which point
`admin-api` owns them and the manifest carries the boot default only. There is no earlier home
for them: a flag store that predates `admin-api` is a service nobody wants to build twice.

**Who flips.** The named owner in the manifest flips in staging freely. Production flips require
the owner plus the release manager, and emit an audit event. The exception is a kill-switch flag
— one whose *off* position is the safe position — which on-call may flip alone, immediately, and
explain afterwards. `p07.ledger.reconciliation_freeze` is the archetype: it ships observe-only,
and the freeze action is a separate flag enabled after two weeks of clean observation.

**Removal.** A flag is removed within one release of its phase gate passing. Enforcement is
mechanical rather than cultural: CI fails a manifest containing a flag whose `introducedIn`
release is more than two releases behind the manifest being generated. A flag that outlives its
phase is not a safety mechanism; it is a second code path nobody tests, and the estate already
demonstrates where that ends — the game client withheld four SKUs from the UI while Pay's routes
stayed live and chargeable.

**What is never behind a flag.** A security fix. A money-correctness fix. A migration step.
Flags gate features, not correctness; a flagged correctness fix is a correctness fix that half
the fleet does not have.

## 7. Deprecation policy

### Internal contracts

Additive-only, enforced by `contract-compat.yml`, which fails on a removed field, a narrowed
type or a renamed key. Removal is therefore a procedure, not a commit:

1. **Deprecate.** The field gains a `@deprecated` annotation with the release it may be removed
   in, and the provider emits a metric counting reads of it.
2. **Census.** The metric answers "is anyone still using this". A field with non-zero reads is
   not removable, regardless of what the consumers claim.
3. **Wait.** Minimum three minor releases of the contract package, and minimum one full release
   train after the last consumer's Renovate bump merged. The 24-hour Renovate target makes the
   waiting period short; if Renovate lag exceeds a week, the topology is failing and removal is
   not the problem to be solving.
4. **Remove**, in a major, with a documented compat-check exception naming the census evidence.

### The public API

From P11: `api.cloudsforge.online/v1` is versioned separately from every internal contract and
on its own cadence. **Two versions supported concurrently. Twelve months' notice.**
Machine-readable `Deprecation`, `Sunset` and `Link` headers on every response from a deprecated
version, plus a notification to every developer organisation with a key that has called it in
the last 90 days, delivered through `notify` rather than by email blast. A version is not
retired while any key has called it in the preceding 30 days without having been individually
contacted.

`api.cloudsforge.online` currently points at the *game* API. It is renamed to `worlds-api.`
before anything depends on it — a rename done in P11, not a deprecation, because at that point
nothing external depends on it at all.

> **CORRECTION 2026-08-07 — this rename was performed and then REVERSED.** The estate serves the
> game API at `api.<apex>/v1/...`, not `worlds-api.<apex>`, and `worlds-api.cloudsforge.online`
> does not resolve. Do not implement what this passage specifies. See
> [18-build-status](18-build-status.md) §0.1 and `ui/packages/ui/src/surfaces.ts`.

## 8. Rollback

### Per-service

Redeploy the previous image digest for one service, leaving the rest of the manifest alone. This
produces a manifest that differs from a released one, so it is recorded as a patch release
(`v0.7.3`) rather than as an untracked edit. Valid only when no expand/contract migration step
sits between the two versions; `cfctl` refuses the deploy when `migrations[]` disagrees, which
is why that field is in the manifest.

### Per-release

Check out the previous manifest, apply, done. This is the designed path and the one rehearsed at
the P2 gate. It recovers code and configuration. It does not undo data.

### Where rollback is impossible

Named here so nobody discovers them mid-incident.

| Irreversible action | Phase | Why it cannot be undone | What is done instead |
| --- | --- | --- | --- |
| **The ledger read cutover, and Pay's balance columns being dropped** | P4 step 5 | Step 4 (reads served from the ledger) *is* reversible for as long as dual write continues — which is exactly why dual write is not switched off at cutover. Step 5 drops the shadow columns, and after that there is no second copy of a balance to fall back to | Dual write is retained for a month past the read cutover. Step 5 happens only after two weeks at zero divergence and is scheduled as its own change with its own approval |
| **Deletion of `POST /admin/keys/:address/reveal`** | P5 | Intentionally irreversible. It is an any-key-to-any-admin exfiltration primitive and restoring it under incident pressure is precisely the scenario it must not survive | The two-operator break-glass runbook ships and is rehearsed **in the same release**, not after |
| **Boot-DDL → versioned migrations** | P2 | One-way per service. Once `schema_migrations` records a baseline and the boot-time `CREATE TABLE IF NOT EXISTS` array is deleted, the old image cannot manage the schema it finds | Proven against a restored production dump before production, one service at a time, least critical first (`forge-mint`). Detail in [10-migration-strategy.md](10-migration-strategy.md) |
| **Contract packages going to `1.0.0`** | P2 | A consumer pinned `^0.4.0` cannot resolve `0.5.0`, and going back to `0.x` after publishing `1.x` is not a thing npm supports | The move is one coordinated pass across all consumers, with the old `0.x` versions left published and resolvable so an emergency revert of a *consumer* still installs |
| **Archiving a legacy repository** | P3, P4, P5 | Reversible in principle, but the replacement has been serving production for a week by then and diverged | Archive read-only with a README pointing at successors; never delete |

For everything else, the rule is: a phase's rollback strategy is stated in
[06-ecosystem-workflow.md](06-ecosystem-workflow.md) and the release cannot be promoted until
that strategy has been demonstrated, not merely written.

## 9. Hotfix

1. **Declare.** A hotfix is a defect that loses money, exposes key material, or breaks a journey
   in production. Nothing else is a hotfix; everything else takes the next weekly train.
2. **Branch from the tag, not from `main`.** `hotfix/<issue>` off the released tag of the *one*
   affected repository. A hotfix touching two repositories is two hotfixes with two manifests, or
   it is not a hotfix.
3. **Patch version.** The repository ships a patch release. No minor, no new field, no schema
   change. If it needs a schema change it is not a hotfix, it is an incident with a migration.
4. **Generate a hotfix manifest** — the released manifest with exactly one digest changed, named
   `v0.7.2` (the patch stream), with the incident id in the manifest metadata.
5. **Gate on a subset.** The affected product's journeys plus the money journeys, on staging, one
   run. The full suite runs afterwards, not before — a hotfix that waits three consecutive full
   runs is not a hotfix. This is the one place the three-run rule is relaxed, and it is relaxed
   deliberately and in writing.
6. **Promote**, two people, and post to the status page if the defect was user-visible.
7. **Forward-port within 24 hours.** The fix merges to `main` with the same regression test, and
   CI fails the next candidate if the hotfix commit is not an ancestor of it. An unforward-ported
   hotfix is a defect scheduled to return.

**Serial spine.** P0 → P1 → P2 admits no parallelism at all. From v0.6 onward the estate runs
two to four tracks, and the practical limit is review capacity rather than dependency — P3's
thirteen extractions are almost entirely independent of one another, and P13's six workstreams
are fully so.

**Critical path.** Summing the serial spine and the longest track through each subsequent
release gives roughly **66 to 96 weeks** from P0 to v1.0. The spread is dominated by three
things, all of which are honest unknowns rather than padding: P2's six-to-ten-week range (the
phase most likely to be under-estimated), P4's soak periods, and P5's 30-day indexer parity
window. None of the three compresses by adding people.

**Where the plan is fragile.** Three dependencies carry the whole schedule. P2's gate blocks
everything. P4's read cutover blocks P5, which blocks P6 and P7, which block everything after.
P9 blocks P10's cross-product journeys. A slip anywhere else is absorbed by a parallel track; a
slip in those three moves v1.0 week for week.
